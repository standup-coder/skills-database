# 提示工程

> 设计、组织并迭代提示词,引导大语言模型产生可靠、有依据的行为。学完本技能,你能把模糊的"帮我写个总结"变成模型稳定执行的清晰指令,并知道模型表现不好时该改哪里。

## 这个技能解决什么问题

大多数人第一次用 LLM 时,遇到的是"模型能聊天但办不成事":让它总结文档,它加戏;让它分类,格式一天三变;让它按步骤来,它跳步。这不是模型笨,而是**提示词没有把任务说清楚**。提示工程解决的就是"人脑任务"到"模型可执行指令"之间的翻译问题。

| 常见痛点 | 不懂提示工程的做法 | 学完后的做法 |
|---|---|---|
| 输出格式不稳定 | 每次靠正则硬解析、天天修 | 在 prompt 里直接规定格式,一次说清 |
| 任务复杂做不好 | 一句话甩给模型,怪模型不行 | 拆步骤、给示例、定约束 |
| 结果忽好忽坏 | 反复换措辞碰运气 | 分清 system/user 角色,单变量调试 |
| 不知道何时该用"逐步思考" | 所有任务都加,越加越差 | 按任务类型判断,知道 cost/benefit |

学完之后你应该能:

- 分清 system / user / assistant 三种消息角色,并把指令放到正确的位置
- 为一个任务写出**具体、分步、带格式要求**的指令,而不是模糊的"请帮我"
- 用正例 + 反例 + 边界样本构造 few-shot,让少样本学习真正生效
- 判断何时该用 Chain-of-Thought,并解释它对简单任务为什么反而有害
- 直觉理解 temperature / top_p 的作用,知道调试时先动谁
- 用"观察失败 → 提出假设 → 单变量修改 → 验证"四步流程系统化地改进 prompt

## 前置知识

本技能是 LLM 应用开发的第一课,硬性前置很少:

1. **会用一种方式调用 LLM**——聊天网页(如 Claude.ai、ChatGPT)即可开始;要做练习里的量化实验,需要能发 API 请求,可参考 [claude-api](../ai-ml/claude-api.md) 了解 API 基本调用方式
2. **理解 token 是什么**——知道输入输出按 token 计费、token 数约等于"模型每次读到的字数的上限"即可,不必会算;更深的窗口管理见 [context-window-management](../ai-ml/context-window-management.md)
3. **会写最基本的 Python**(仅练习/示例部分需要)——能跑一个脚本、打印结果就够

如果你从零开始:先随便找一个聊天界面,用学到的概念逐个实验本技能示例里的 prompt,再进入 API 调用练习。不需要先学其他技能。

## 核心概念

按"理解 → 应用"排序,共六个概念。前四个解决"怎么说",第五个解决"要不要多想",第六个解决"怎么调参数"。

### 1. 消息结构与三种角色

LLM 对话接口把输入组织成**消息列表**,每条消息有一个角色。绝大多数模型只用三种角色:

| 角色 | 作用 | 典型内容 | 类比 |
|---|---|---|---|
| `system` | 定义模型的身份、任务大背景、全局规则 | "你是客服质检员,评价客服回复质量" | 岗位说明书 |
| `user` | 本轮的具体输入、请求 | "这段对话的客服回得怎么样?" | 客户来问 |
| `assistant` | 模型自己的回复;也可由你**伪造**作为示例 | "评分:A,理由:…" | 员工交活 |

三个关键实践:

- **system 里放"不变的规则",user 里放"每次变化的输入"**。把问题本身写进 system,换一个输入就要重写整段系统提示,等于放弃复用。
- **用 assistant 角色伪造对话示例(few-shot)**,这比把示例塞进 system 一段话里更符合模型训练时的数据形态,效果通常更好。
- 后续多轮对话中,历史消息按 user/assistant 交替追加;**不要自己发明第四种角色**(如 `instruction`),大多数 API 会直接报错或忽略。

### 2. 角色设定(persona)

给模型一个明确的**身份 + 视角**,让它从"一个万能聊天机器人"收缩到"一个特定的专业人员"。角色本身压缩了输出空间的风格与边界——你不需要在 prompt 里逐条规定"不要写废话",一个"严谨的审计师"角色天然倾向简洁、谨慎。

好的角色设定三要素:

1. **身份**:你是谁(岗位、专业背景)
2. **视角/立场**:你从什么角度看问题(比如既看用户体验也看合规)
3. **边界**:你不做什么(可选,重要的"不要"单独写)

```text
你是资深客服质检员,有 5 年呼叫中心质检经验,
评估标准参照《客服服务规范 3.0》。
你只评估回复质量本身,不评价用户的用词。
```

> 注意:角色设定是**补充信号**,不是万能药。它约束风格有用,但约束"输出格式""禁止编造"等硬规则,要靠下文的清晰指令与消息结构,不能指望角色代劳。

### 3. 清晰指令写作:具体、分步、给格式

模型无法读出你的潜台词。指令写作的三条铁律:

**① 具体——用"度量"代替"感觉"**

| ❌ 模糊 | ✅ 具体 |
|---|---|
| "总结这段话" | "用 3 句话总结,每句不超过 30 字,只提取事实不添加评价" |
| "帮我润色" | "改写为正式书面语,保持原意,删除重复表达,输出 200-300 字" |
| "检查错误" | "逐条核对数字与日期,发现不一致输出 ❌ 并列出原文与修正" |

**② 分步——复杂任务拆成编号步骤**

模型对"一步到位的复杂请求"经常漏做其中一半。把流程写出来,等于把任务的执行顺序也交出去:

```text
请按以下步骤处理:
1. 通读全文,提取所有数字指标
2. 核对每个指标在文中的出处
3. 按「指标(出处页数)」格式输出清单
4. 若某指标无出处,标注「无出处」而不是猜测
```

**③ 给格式——先给模板,再要内容**

"给格式"比"规定格式"更可靠:直接给一个模板让模型填空,比用文字描述"要一个 JSON,里面有 name、age 字段"稳定得多。输出规范放 system 或 user 末尾,用代码块框起来:

```text
输出格式(只输出 JSON,不要多余文字):
{
  "sentiment": "positive | negative | neutral",
  "confidence": 0.0-1.0
}
```

### 4. Few-shot:用示例教模型

模型能从少量(2-10 个)示例中学会任务模式,这叫 in-context learning。示例的质量决定学习效果,三条原则:

- **覆盖三类样本**:正例(该怎么做)+ **反例**(不该怎么做,直接写"这是错误示范")+ **边界样本**(容易混淆的输入,如"外卖迟到但客服态度很好"该分 negative 还是 mixed)
- **示例风格 = 期望输出风格**:模型会模仿示例的长度、语气、格式。想要简洁输出,示例就必须简洁
- **数量不是越多越好**:5-8 条通常够用,再多会稀释注意力、增加 token 成本

```text
把用户反馈分类为 positive / negative / neutral:

反馈:"包装很精致,味道也好" → positive
反馈:"外卖迟到一小时,汤都洒了" → negative
反馈:"还行吧,和上次差不多" → neutral
反馈:"客服态度不错,但退款流程太慢" → (边界,答案是 mixed 就先教 mixed)
反馈:"东西是坏的,但客服二话不说给换了" → mixed
```

**重要**:few-shot 示例要来自与线上**不同批**的真实数据,且与评估集严格分离,否则会发生数据泄漏——线上表现虚高,一上生产就现原形(详见 [llm-evaluation](../ai-ml/llm-evaluation.md))。

### 5. Chain-of-Thought:什么时候该"逐步思考"

CoT(Chain-of-Thought)是让模型**把推理过程写出来再给答案**。对需要多步推理的任务(数学、逻辑、多跳问答),它显著提升准确率;对简单任务(情感分类、关键词抽取),它引入无关推理、增加 token、还可能把明显答错的说成对的。

| 任务类型 | 用 CoT? | 原因 |
|---|---|---|
| 数学/逻辑/多跳推理 | ✅ 用 | 推理链可纠正中间错误 |
| 代码生成 | ✅ 可用 | 先想思路再写码 |
| 分类/抽取 | ❌ 不用 | 推理是噪音,输出变长变贵 |
| 翻译 | ❌ 不用 | 直接翻译更准 |

入门用法只有两种:

1. **零样本 CoT**:在任何 prompt 末尾加一句"请逐步思考后再给出最终答案"(或英文 Let's think step by step)。零成本、无示例,是默认起点。
2. **示例式 CoT**:在 few-shot 里给出"输入 → 思考过程 → 答案"的完整样例,让模型模仿推理格式。

> 判断标准一句话:这个任务"只要想一步就能答"就不需要 CoT;需要"想好几步、且中间步容易错"就需要。任务拆步骤(概念 3)和 CoT 不冲突——前者是命令模型按顺序做,后者是命令模型把思考写出来。

### 6. temperature 与 top_p:随机性的两个旋钮

模型生成时不是"选最可能的词",而是"按概率分布采样"。temperature 和 top_p 控制采样行为:

| 参数 | 控制什么 | 调小的效果 | 调大的效果 | 直觉 |
|---|---|---|---|---|
| `temperature`(0-2) | 整体随机性 | 输出确定性高、偏保守 | 更有创意、更发散 | 让分布"变尖"还是"变平" |
| `top_p`(0-1) | 采样候选池大小 | 只从最高概率的词里选 | 候选池大,敢说冷门词 | 只留"头部概率"还是全都要 |

**调试铁律**:

- 追求**稳定、可复现**(分类、抽取、结构化输出)→ `temperature=0`(部分 API 还支持 seed 参数进一步固定采样)。服务端并发一样的结果,才谈得上评估。
- 追求**创意**(文案、头脑风暴、起名)→ temperature 0.7-1.0。
- **先调 temperature,再动 top_p**。top_p 只在 temperature 效果不够时作为第二旋钮,绝大多数场景固定 top_p=1 即可。
- 每次实验**只动一个参数**,否则不知道是谁的功劳。

## 学习路径

按 4-6 周规划。每阶段验收标准达标再进入下一阶段,中途卡住就回看对应核心概念。

### 阶段一:会说人话给模型听(第 1 周)

**目标**:能写出"具体、分步、给格式"的指令,并解释消息三角色的分工。

- 掌握 system / user / assistant 的用途与放什么
- 掌握"具体/分步/给格式"三条铁律
- 会写简单的角色设定

**验收标准**:

- [ ] 拿一个你手头的真实任务(如周报总结、评论分类),分别写"模糊版"和"规范版"两版 prompt,说出规范版改了三处什么
- [ ] 说出 system 和 user 各放什么内容,并给出一个"该放 system 却放进了 user"的反例
- [ ] 用规范版 prompt 连续问同一个问题 3 次,输出格式完全一致

### 阶段二:用示例和思考链提升正确率(第 2-3 周)

**目标**:会用 few-shot 与 CoT 提升任务质量,并能判断二者的适用边界。

- 掌握正例 + 反例 + 边界样本的 few-shot 写法
- 掌握零样本 CoT 与示例式 CoT,能说出各自成本
- 知道什么任务不该用 CoT

**验收标准**:

- [ ] 选一个分类任务,构造 5-8 条 few-shot(含至少 1 条反例、1 条边界样本),跑通并对比零样本 vs few-shot 的输出差异
- [ ] 构造一个多步计算任务,对比"直接问"vs"请逐步思考"的两种结果,记录哪个对
- [ ] 能说出为什么分类任务加了 CoT 反而变慢变贵

### 阶段三:参数控制与迭代调试,独立交付(第 4-6 周)

**目标**:能独立完成一条 prompt 的调试闭环并量化改进,达到可交付水平。

- 掌握 temperature / top_p 对输出的影响与调试顺序
- 掌握"观察失败 → 假设 → 单变量修改 → 验证"的迭代流程
- 会为 prompt 建立最小评估基线(10-20 条测试输入)

**验收标准**:

- [ ] 对任一任务跑通完整迭代流程:建基线 → 发现 ≥2 类失败 → 提出假设 → 修改 → 对比分数提升,留下记录
- [ ] 说出"结果忽好忽坏"时先调什么参数,并实测验证
- [ ] 交付一条你认为稳定的 prompt,附上:结构说明(消息角色/示例/约束)、测过的边界情况、已知限制

## 分步实操:一次完整的提示优化

下面的流程适用于任何"输出不理想"的场景。关键纪律:**先有基线,再动手改**——否则你永远在"调感觉"。

```
第 1 步 明确任务与成功标准      → 输入:模糊需求;输出:一句话任务 + 可验收标准
   ↓
第 2 步 构建最小评估集(10-20 条) → 输出:输入输出样本清单
   ↓
第 3 步 跑 v0 基线,记录失败样本   → 输出:基线结果 + 失败清单
   ↓
第 4 步 对失败分类,提出假设        → 输出:每类失败的修改假设
   ↓
第 5 步 单变量修改,跑分对比        → 输出:v1 分数 vs 基线分数
   ↓
第 6 步 记录结果,固化版本          → 输出:版本说明(改了什么/分数/遗留问题)
```

### 第 1 步:明确任务与成功标准

把需求写成一句话:输入是什么、输出是什么、给谁用。再写 2-3 条可验收标准(格式稳定?信息不丢?答错率低于 X?)。**标准写不出来,后面全是玄学。**

### 第 2 步:构建最小评估集

从真实使用中收集 10-20 条输入,覆盖三类:正常输入、容易混淆的边界输入、你的 prompt 可能搞不定的刁钻输入。把期望输出(或验收规则)记在旁边。规模小没关系,重要的是**固定不变**——它以后是你的对照尺。

### 第 3 步:跑 v0 基线

用最简单的 prompt(只有任务描述,不加任何技巧)跑一遍评估集,把每条输出存下来。**基线不是用来"好"的,是用来"对比"的。**

### 第 4 步:失败分类与假设

把失败输出归类,例如:格式不符(说了 JSON 给了一堆字)、信息遗漏(总结丢了关键数字)、幻觉(加了原文没有的内容)、风格不符。每类失败对应一种修改假设:

| 失败类型 | 典型假设 | 对应手段 |
|---|---|---|
| 格式不符 | 模型没理解输出规范 | 给格式模板 / 缩短要求 |
| 信息遗漏 | 指令没有覆盖到 | 拆步骤,逐条列出 |
| 幻觉/编造 | 模型在"补全"而非"引用" | 明确"只依据给定内容,不添加" |
| 边界不清 | 示例不够 | 加反例、边界样本 |

### 第 5 步:单变量修改

一次只针对**一类失败**改**一个变量**(加示例 / 改措辞 / 调 temperature / 换角色)。跑分,保留提升项;**分数不变或下降就回滚**。目标不是"一次到位",是"每次改动可解释"。

### 第 6 步:记录与版本化

把每一步改动记下来:改了什么、基线分数 → 新分数、留下什么问题。prompt 纳入 git 管理,commit message 写清动机。下次模型升级或需求变更,你才能回答"这个 prompt 为什么长这样"。

## 示例

三个完整示例,建议逐个跑通。示例 1、2 覆盖本技能核心手法,示例 3 是把前面所有概念串起来的调试闭环。运行前请自行设置 `OPENAI_API_KEY`(或换成你使用的任意模型 API)。

### 示例 1:指令优化前后对比

同一个任务——把会议记录压缩成三条行动项——用"模糊版"和"规范版"各跑一次,观察输出差异。

```python
# 指令优化前后对比示例
from openai import OpenAI  # 可替换为其他厂商 SDK,消息结构相同

client = OpenAI()

MEETING = """2026-10-20 产品周会:
张伟汇报数据看板二期进展,预计 11 月 10 日上线,还差接口联调。
李娜提到用户反馈工单积压,建议加自动分类,需产品出规则。
王芳确认市场活动 11 月 1 日启动,物料周五前交付设计。
会议决定:下周三前各人给出排期,邮箱同步给全员。"""

BAD_PROMPT = "帮我总结一下这段会议记录。"  # 模糊版:什么都没有说清

GOOD_PROMPT = f"""你是会议纪要整理助手。请把会议记录压缩成行动项清单。

处理步骤:
1. 找出所有"谁要在什么时间前做什么"的信息
2. 压缩成 3 条以内,每条不超过 40 字
3. 没有明确责任人或截止日期的信息不写进清单

会议记录:
{MEETING}

输出格式(只输出清单,不要其他文字):
- [负责人] 行动项(截止日期)
"""

for name, prompt in [("模糊版", BAD_PROMPT), ("规范版", GOOD_PROMPT)]:
    resp = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": prompt}],
        temperature=0,  # 想对比 Prompt 本身,先固定随机性
    )
    print(f"===== {name} =====\n{resp.choices[0].message.content}\n")
```

**要点**:两个版本唯一区别在 prompt 本身(参数、模型都固定)。模糊版输出是"一段概述",可能漏掉"11 月 1 日";规范版通过拆步骤 + 给格式 + 定字数,把"压缩"这个模糊动词变成了可执行规则。**对比实验时只动要对比的变量,是提示工程的第一纪律。**

### 示例 2:分类任务 few-shot(正例 + 反例 + 边界样本)

把用户反馈分为 `positive / negative / mixed`,重点演示边界样本和反例的作用。

```python
# 分类任务 few-shot 示例
from openai import OpenAI

client = OpenAI()

# 正例:标准情况;反例:教模型"不要被字面带偏";边界样本:好坏参半
FEW_SHOT = """把用户反馈分为 positive / negative / mixed 三类,只看整体体验,不只看单点。

反馈:包装很精致,味道也好,五星! → positive
反馈:外卖迟到一小时,汤全洒了 → negative
反馈:客服态度不错,不过退款流程太慢 → mixed
反馈:东西不错但快递太慢,总的来说还行 → mixed
反馈:退款成功,平台给力 → positive

反馈:"""

# 边界测试样本:字面上有"好"和"坏",看模型是否被示例引导
TEST_CASES = [
    "便宜是便宜,但质量一言难尽",           # 整体偏 negative
    "虽然有缺点,但比上一个商家强多了",     # 整体偏 positive
    "一般般吧,没有惊喜也没有意外",         # mixed
]

for text in TEST_CASES:
    resp = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": FEW_SHOT + text}],
        temperature=0,
    )
    print(f"{text} → {resp.choices[0].message.content.strip()}")
```

**要点**:示例中的 `mixed` 样本就是"边界样本"——它们让模型知道存在第三类,避免把"好坏参半"硬归到 positive/negative 之一。第二条示例还演示了"以整体体验为准"的判定规则。**示例不是在"喂答案",是在"教分类规则"**;规则越需要体现,边界样本越不能省。

### 示例 3:迭代调试最小闭环(带基线的完整循环)

把本技能的流程串起来:固定评估集 → 跑基线 → 单变量修改 → 对比分数。任何 prompt 改动都应在这类脚本里进行,而不是在聊天框里"看感觉"。

```python
# 提示迭代调试最小闭环
from openai import OpenAI

client = OpenAI()

# 固定评估集:输入 → 期望类别(第 2 步的产物,之后不要轻易改)
EVAL_SET = [
    ("包装很精致,味道也好", "positive"),
    ("外卖迟到一小时,汤都洒了", "negative"),
    ("客服不错但退款太慢", "mixed"),
    ("便宜但质量一言难尽", "negative"),
    ("比上一个商家好多了", "positive"),
    ("一般般,没惊喜也没意外", "mixed"),
    ("退款成功,平台给力", "positive"),
    ("第二次买,还是发错货", "negative"),
]

PROMPT_V0 = "把反馈分为 positive / negative / mixed。"           # 基线:啥技巧都没有
PROMPT_V1 = "把反馈分为 positive / negative / mixed。只看整体体验。"  # v1:加判定规则

def classify(prompt: str, text: str) -> str:
    resp = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": f"{prompt}\n\n反馈:{text}"}],
        temperature=0,
    )
    return resp.choices[0].message.content.strip().lower()

def run_version(prompt: str):
    """跑完整个评估集,返回准确率与出错样本(第 3、5 步)。"""
    correct = 0
    errors = []
    for text, gold in EVAL_SET:
        pred = classify(prompt, text)
        if pred == gold:
            correct += 1
        else:
            errors.append((text, gold, pred))
    return correct / len(EVAL_SET), errors

for version, prompt in [("v0 基线", PROMPT_V0), ("v1", PROMPT_V1)]:
    acc, errors = run_version(prompt)
    print(f"{version}  准确率: {acc:.0%}  出错: {errors}")

# 预期:v0 可能把边界样本分错,v1 通过"只看整体体验"纠正一部分
# 下一步:如果 still 有错,再考虑加 few-shot 示例(单变量原则:每次只加一类手段)
```

**要点**:脚本里的 `EVAL_SET` 就是你的"尺子";`PROMPT_V1` 只改了一个变量(加判定规则);`temperature=0` 保证分数可复现。**把调试从"聊天框里试"搬进脚本,是提示工程从爱好变成工程的分水岭。**

### 基础练习

- [ ] **P1-1 模糊版 vs 规范版**:选一个真实任务(周报总结、邮件改写、发票信息抽取),写模糊版与规范版各一,各跑 3 次,记录两者的格式稳定性差异(产出:两份 prompt + 观察记录)

- [ ] **P2-1 few-shot 三样本**:为 P1-1 的任务构造 5-8 条 few-shot(含 ≥1 反例、≥1 边界样本),与零样本对比准确率,记录提升量

- [ ] **P3-1 完整迭代闭环**:对任一任务按"分步实操"六步走完:基线 → ≥2 类失败 → 两次单变量修改 → 分数对比,产出迭代记录表(版本、改动、基线→新分数)

## 自测题

先独立作答,再对照题后答案。答不出的题回看对应章节。

1. 你有一个任务:每轮输入不同的商品评论,要求固定输出 JSON 字段。请问:任务描述与输出格式模板放 system 还是 user?为什么?
2. "你是资深审计师"这种角色设定,能解决输出格式问题吗?为什么?
3. 指令"帮我看看这段代码"为什么不好?按三条铁律改成可执行版本。
4. few-shot 中"反例"和"边界样本"各自解决什么问题?各举一个场景。
5. 什么任务不该用 CoT?为什么?
6. 生产环境的分类接口输出忽好忽坏,你应该先检查哪个参数?调试顺序是什么?
7. "结果看起来不错"为什么不能作为 prompt 改动的验收证据?
8. 你的 prompt v1 比 v0 准确率高了,但你不确定是加了示例还是改了措辞的功劳。问题出在哪?正确做法是什么?

<details>
<summary>答案</summary>

1. 任务描述与格式模板放 system(不变的部分);商品评论放 user(每轮变化的部分)。system 放规则、user 放输入,才能复用系统提示并保持结构清晰。
2. 不能。角色设定主要约束风格与视角,是"软信号";输出格式是"硬规则",要靠明确的格式模板 + 消息结构,不能指望"审计师"自动输出 JSON。
3. 至少三处:具体化(检查什么——语法/逻辑/安全/性能)、分步(先定位问题再给建议)、给格式(按"问题:… 严重度:… 建议:…"输出)。
4. 反例解决"模型不知道不该怎么做",如分类任务里教它"不要把整体好评但因为一个小问题分为 negative";边界样本解决"两类之间怎么划界",如"客服不错但退款慢"这类好坏参半的输入。
5. 简单分类、抽取、翻译等一步能答的任务。CoT 引入无关推理,增加 token 与耗时,还可能让简单问题被"想复杂"而答错。
6. 先检查 temperature(应设为 0)与 seed;调试顺序:先固定 temperature/top_p,再改 prompt 内容,每次只动一个变量。
7. "看起来不错"无法量化、无法复现、无法对比;"好/坏"的判断会随心情漂移。验收证据必须来自固定评估集上的分数对比。
8. 一次改了多个变量,违反了单变量原则。正确做法:回滚到 v0,分别做"只加示例"和"只改措辞"两次独立实验,各自对比基线。

## 常见错误与反模式

- ❌ **模糊动词当指令**("帮我总结/优化/分析一下")——模型只能猜你的标准。用具体、分步、给格式的三铁律重写
- ❌ **把每次变化的输入写进 system**——换输入就要重写系统提示,失去复用性;system 放规则,user 放输入
- ❌ **所有任务都加"请逐步思考"**——简单任务变慢变贵还变差;按"是否多步推理"判断
- ❌ **few-shot 示例风格与期望输出不一致**——示例长度 500 字却要求输出 10 字,模型学的是示例不是你的要求
- ❌ **few-shot 与评估集同源**——数据泄漏,线上准确率虚高(见 [llm-evaluation](../ai-ml/llm-evaluation.md))
- ❌ **结果不稳定时先改 prompt 而不是先查 temperature**——先用 temperature=0 排除随机性,再谈 prompt 问题
- ❌ **一次改多个变量**——加示例 + 换角色 + 调温度,分数变了不知道是谁的功劳
- ❌ **没有基线就开始调**——没有对照点,所有修改都无法判断好坏;至少先留 10-20 条固定测试输入
- ❌ **把"看起来不错"当证据**——固定评估集 + 分数才是证据(参考 [llm-evaluation](../ai-ml/llm-evaluation.md))
- ❌ **依赖自由文本解析**——能用 JSON/结构化输出就让模型直接给结构化结果,别用正则擦屁股(进阶见 [prompt-engineering-advanced](../ai-ml/prompt-engineering-advanced.md))
