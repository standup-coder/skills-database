# E2E 测试策略

> 建立"少而稳"的端到端测试体系：金字塔定位、关键旅程选取、稳定性工程与 flaky 治理的完整闭环

## 何时使用

- 产品有了核心用户旅程（注册/下单/支付），需要发布级的信心保障
- 现有 E2E 套件又慢又 flaky，团队开始习惯性重跑甚至忽略红灯
- 从手工回归转向自动化，需要决定"哪些场景值得写 E2E"

## 何时不使用

- 单元/集成测试尚未覆盖核心逻辑——先补金字塔下层，E2E 补不了下层的洞且贵 10 倍
- UI 每周大改的早期探索产品——E2E 维护成本会吞噬全部收益，先用冒烟级少量用例

## 工作流

```
[输入: 用户旅程清单 + 现有测试资产]
  ↓
步骤 1: scope — 金字塔定位与旅程选取
  ↓
步骤 2: design — 用例设计与测试数据策略
  ↓
步骤 3: implement — 稳定性优先的实现
  ↓
步骤 4: operate — CI 集成与 flaky 治理
  ↓
[输出: 快速、可信、可维护的 E2E 套件]
```

### 步骤 1: scope

**目标**：明确 E2E 在测试金字塔中的定位——只覆盖"跨系统集成才能验证的关键用户旅程"，其余下沉到单元/集成/契约测试。
**输入**：用户旅程清单（按业务价值排序）、现有各层测试覆盖情况。
**输出**：E2E 范围清单（通常 10-30 条旅程，如注册登录/核心交易/支付）、每条的准入理由、明确的"不做清单"（能用集成测试验证的一律不写 E2E）。
**失败处理**：业务方要求"全部场景都要 E2E"时，用维护成本数据谈判（每条 E2E 的年维护成本远超编写成本）；发现某旅程其实只测一个服务时，降级为集成测试。

### 步骤 2: design

**目标**：为每条旅程设计用例与数据策略：用例只断言用户可见结果（而非实现细节），测试数据做到隔离、可重建、互不干扰。
**输入**：步骤 1 的范围清单、环境与账号体系现状。
**输出**：用例设计文档（每条含前置状态/操作序列/断言点）、数据策略（API 播种优先于 UI 造数、每条用例独立命名空间、用后清理或环境定期重置）。
**失败处理**：用例间共享账号/数据导致相互污染时，强制每条用例自建隔离数据；前置状态靠十几步 UI 操作搭建时，改为 API/DB 直接播种，UI 只走被测路径。

### 步骤 3: implement

**目标**：稳定性优先的实现：语义化定位器（role/label/test-id，杜绝脆弱的 CSS 链）、自动等待替代固定 sleep、Page Object/fixture 组织复用逻辑。
**输入**：步骤 2 的用例设计，选定框架（Playwright/Cypress）。
**输出**：可在本地与 CI 稳定运行的测试代码，失败时自带排障产物（screenshot/video/trace）。
**失败处理**：本地十连跑（`--repeat-each=10`）不绿的用例禁止合入；定位器频繁失效时推动产品代码补 test-id，而不是写更复杂的选择器。

### 步骤 4: operate

**目标**：让套件长期可信：接入 CI 分级运行（PR 冒烟子集 + 合并后全量）、并行分片压缩时长、flaky 检测与隔离流程、失败必须有人认领。
**输入**：步骤 3 的套件、CI 平台。
**输出**：CI 流水线配置（分级/分片/重试策略）、flaky 看板（自动标记连续 pass-fail 抖动的用例并移入隔离区限期修复）、套件健康度指标（时长/通过率/flaky 率）。
**失败处理**：出现"红灯但大家照常合码"时立即止血——隔离所有 flaky 用例让主干恢复可信，再逐个修复回收；套件时长超过 15 分钟时加大分片并审视范围清单是否膨胀。

## 输入参数

- `user_journeys`（必填）— 按业务价值排序的用户旅程清单
- `existing_tests`（可选）— 各层现有测试覆盖情况
- `ci_platform`（可选）— CI 环境与并行资源约束

## 输出

- 定位清晰的 E2E 范围清单与不做清单
- 稳定可维护的测试套件（含数据策略与排障产物）
- CI 分级运行 + flaky 治理的运营机制

## 学习要点

- E2E 的价值在"少而稳"：30 条稳定的关键旅程测试 > 300 条 flaky 的全量测试——后者的红灯没人信，等于没有测试
- flaky 是套件的癌症：对随机失败的容忍度必须为零，重跑通过不等于没有问题（往往是真实的竞态）
- 测试数据策略决定成败：绝大多数"E2E 很难维护"的根因是数据耦合而不是工具问题
