# ML 实验工作流

> 从问题定义到模型上线候选的可复现实验闭环：基线先行、实验跟踪、严格评估、注册交付

## 何时使用

- 建模任务超出一次性脚本范畴，需要多轮迭代且团队要能复现任意历史实验
- 多人协作调参/换特征/换模型，结论开始互相矛盾（"我这边分数更高"）
- 模型要交付上线，需要清晰的候选版本管理与评估证据链

## 何时不使用

- 一次性探索分析（EDA）或纯统计推断——用轻量 notebook 即可
- 直接调用现成 API（LLM/预训练模型）不训练自有模型——评估仍需要但训练流程不适用

## 工作流

```
[输入: 业务问题 + 可用数据]
  ↓
步骤 1: frame — 问题定义与成功指标对齐
  ↓
步骤 2: baseline — 数据切分 + 最简基线
  ↓
步骤 3: iterate — 假设驱动的实验迭代（全程跟踪）
  ↓
步骤 4: evaluate — 候选模型的严格离线评估
  ↓
步骤 5: register — 模型注册与交付物打包
  ↓
[输出: 可复现的上线候选模型 + 完整证据链]
```

### 步骤 1: frame

**目标**：把业务问题翻译成 ML 问题：预测什么、用什么指标衡量、达到多少才值得上线（与业务方书面对齐）。
**输入**：业务目标、约束（延迟/可解释性/合规）。
**输出**：问题定义文档：预测目标与粒度、主指标 + 护栏指标、最低上线线（相对现状方案的提升幅度）。
**失败处理**：业务方说不清"多准才够"时，先量化现状方案（规则/人工）的表现作为参照系；目标无法定义清楚时停止建模，回到业务分析。

### 步骤 2: baseline

**目标**：先切分再动手：确定防泄漏的数据切分方案（时序数据必须按时间切分），跑通最简基线（多数类/均值/简单规则/线性模型）。
**输入**：步骤 1 的问题定义、原始数据。
**输出**：固定的 train/validation/test 切分（test 上锁，全程只用一次）、基线分数、端到端可运行的 pipeline 骨架。
**失败处理**：基线已接近上线线时质疑是否需要复杂模型；基线异常高时排查标签泄漏（最常见：特征里混入了结果的代理变量）。

### 步骤 3: iterate

**目标**：假设驱动迭代：每个实验先写假设（"加入 X 特征应提升 Y 因为 Z"），用实验跟踪工具（MLflow/W&B）记录代码版本、数据版本、参数、指标、产物。
**输入**：pipeline 骨架、特征/模型候选假设清单。
**输出**：实验记录序列（每条可一键复现）、validation 集上的最佳候选集合。
**失败处理**：分数无法复现时检查随机种子、数据版本、依赖版本三件套；连续多轮无提升时回到误差分析（看模型错在哪类样本）而不是继续盲调参。

### 步骤 4: evaluate

**目标**：对最终候选做一次性 test 集评估 + 切片分析（按用户群/时间段/难度分层），确认不存在整体分数掩盖的局部劣化。
**输入**：步骤 3 的候选模型、上锁的 test 集。
**输出**：评估报告：主指标 + 护栏指标 + 切片表现 + 校准曲线 + 与基线/现状的对比结论。
**失败处理**：test 分数显著低于 validation 时说明迭代过程过拟合了 validation——重新切分并缩减候选空间；某切片显著劣化时评估业务影响，必要时分群建模。

### 步骤 5: register

**目标**：把通过评估的模型注册为版本化交付物：模型文件 + 特征定义 + 预处理逻辑 + 评估报告 + 训练数据快照引用，交付给部署流程。
**输入**：步骤 4 通过的候选模型与评估报告。
**输出**：model registry 中的版本化条目（含 lineage：数据→代码→参数→产物），交接文档（含已知局限与监控建议）。
**失败处理**：线上特征无法与训练时对齐（training-serving skew）时回到特征工程约定统一逻辑；交付后发现问题需回滚时，registry 的版本化保证任意历史版本可重新部署。

## 输入参数

- `business_problem`（必填）— 业务目标与约束条件
- `data_sources`（必填）— 可用数据及其更新频率
- `serving_constraints`（可选）— 上线环境的延迟/资源/合规约束

## 输出

- 通过严格评估的上线候选模型（registry 版本化条目）
- 全程可复现的实验记录与评估证据链
- 含已知局限与监控建议的交接文档

## 学习要点

- test 集只许用一次：反复看 test 分数选模型 = 把 test 变成第二个 validation，上线后必然低于预期
- 实验跟踪不是流程负担而是团队记忆：三个月后"当时为什么选这个特征"只有记录能回答
- 误差分析 > 盲目调参：看清模型错在哪类样本，比网格搜索多 100 组参数更有产出
